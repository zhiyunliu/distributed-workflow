# 规格拆分索引

本文档根据 [docs/requirement.md](../docs/requirement.md) 将统一流程编排平台拆分为多个可独立规划、实现和验收的 SpecKit 规格。拆分遵循项目宪章 v1.0.0：统一元模型优先、双引擎隔离、glue 框架优先、SQL Server 企业级持久化与审计、公开 JSON 键名使用小写下划线。

## 规格列表

| 编号 | 规格 | 目标 | 建议阶段 |
| --- | --- | --- | --- |
| 001 | [统一元模型与存储](001-unified-model-storage/spec.md) | 定义流程模型、版本表、模型校验和 SQL Server 存储基础。 | 第一阶段 |
| 002 | [引擎路由与统一 API](002-engine-router-api/spec.md) | 提供流程定义、发布、执行、调试、导入导出的统一入口。 | 第一阶段 |
| 003 | [自研规则链引擎核心](003-rulechain-engine-core/spec.md) | 实现规则链 DAG 校验、节点调度、连线路由和基础节点扩展。 | 第一阶段 |
| 004 | [工作流引擎核心](004-workflow-engine-core/spec.md) | 实现长周期实例、人工任务、状态恢复、事务补偿和节点日志。 | 第二阶段 |
| 005 | [跨引擎标准联动](005-cross-engine-linkage/spec.md) | 通过标准节点实现工作流调用规则链、规则链启动工作流。 | 第二阶段 |
| 006 | [统一可视化流程设计器](006-visual-flow-designer/spec.md) | 提供双模式画布、节点工具箱、属性面板、实时校验和导入导出。 | 第一至二阶段 |
| 007 | [运行观测与审计治理](007-observability-audit/spec.md) | 统一执行日志、节点日志、链路追踪、审计查询和运营视图基础。 | 第三阶段 |

## 推荐执行顺序

1. 先执行 001，稳定统一模型和核心表结构。
2. 再执行 002，建立 API、路由、版本和统一响应契约。
3. 并行推进 003 与 006 的规则链 MVP：规则链核心可执行，设计器可保存和校验规则链草稿。
4. 推进 004，补齐工作流长周期能力。
5. 在 003 和 004 的基础上执行 005，避免跨引擎联动提前耦合内部上下文。
6. 最后执行 007，将高频日志、审计、追踪和运营查询治理成体系。

## 全局约束

- 所有公开 API、数据库 JSON、导入导出模型示例必须使用小写下划线 JSON 键名，例如 `flow_code`、`from_id`、`to_id`、`relation_type`、`is_default`。
- 后端实现必须基于 `github.com/zhiyunliu/glue`，优先复用 glue 的 API、中间件、缓存、日志、监控和服务治理能力。
- `WORKFLOW` 与 `RULE_CHAIN` 内核不得共享运行时上下文，不得直接跳转对方节点。
- 查询类接口使用 GET，创建、修改、删除、发布、执行、调试类接口使用 POST。
- API 响应使用 `code`、`message`、可选 `data`；错误响应必须包含 `sub_code`。
