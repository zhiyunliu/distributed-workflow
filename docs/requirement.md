# 统一流程编排平台项目说明文档
## 一、项目概述
### 1.1 项目背景
企业数字化场景中同时存在两类核心流程需求：一类是长周期、有人工参与、需要状态持久化的业务流程（如审批流、工单流转、订单生命周期管理，典型代表为微软 WF 工作流框架）；另一类是高并发、无状态、事件驱动的实时数据处理链路（如物联网数据告警、消息路由、数据转换，典型代表为 Go 生态 RuleGo 规则引擎）。

两类流程传统方案相互割裂，存在设计体验不统一、存储规范不一致、能力无法联动、运维成本高等问题。本项目旨在打造一套**统一元模型、统一设计入口、双引擎内核隔离**的流程编排平台，同时兼容重型工作流与轻量规则链两类场景，实现一套系统覆盖全流程业务需求。

### 1.2 核心目标
1. **体验统一**：一套可视化设计器支持两种流程模式，拖拽交互、操作逻辑完全一致，降低用户学习成本。
2. **存储统一**：一套标准化元模型承载所有流程定义，统一数据库存储规范，支持版本管理与全链路审计。
3. **能力互补**：工作流引擎覆盖长时运行、人工协作、事务管控能力；规则链引擎覆盖高并发、低延迟、事件处理能力，二者可双向联动。
4. **架构松耦合**：双引擎内核完全隔离、独立演进，通过路由层对外提供统一服务，故障互不影响，支持独立扩容。
5. **自主可控**：规则链引擎纯自研实现，无第三方引擎依赖；技术栈基于 glue 微服务框架统一承载，中间件能力复用框架原生实现，减少外部依赖。

## 二、总体设计原则
1. **存储优先，模型先行**：以统一显式边集为核心存储标准，先定义元模型规范，再向上支撑设计器、向下支撑引擎执行。
2. **引擎隔离，能力边界清晰**：不强行融合两种执行模型，工作流与规则链内核完全解耦，通过标准接口联动，避免模型混乱。
3. **扩展友好，开闭原则**：节点类型、执行逻辑、扩展组件均通过接口化注册实现，新增能力无需修改内核代码。
4. **框架复用，减少冗余**：后端服务、缓存、日志监控全链路复用 glue 框架原生能力，不重复造轮子，降低运维与开发成本。
5. **企业级适配**：全面适配 SQL Server 数据库，支持事务、审计、多版本管理等企业级特性。

## 三、整体架构设计
### 3.1 架构分层
采用五层分层架构，自上而下职责清晰，各层仅与相邻层交互，降低耦合度；底层基础能力全部复用 glue 框架原生组件。

| 架构层级 | 核心职责 | 关键组件 |
|----------|----------|----------|
| 可视化设计层 | 统一图形化建模、流程配置、调试预览 | 流程设计器、节点工具箱、属性配置面板 |
| 统一元模型层 | 流程定义标准化、模型校验、格式转换 | 统一JSON Schema、模型校验器、格式映射器 |
| 引擎路由层 | 请求分发、版本管理、统一API入口、权限管控 | 流程路由分发器、统一API服务、版本管理器 |
| 双引擎内核层 | 流程逻辑执行、状态管理、节点调度 | 工作流引擎、自研规则链引擎、扩展节点工厂 |
| 基础设施层 | 数据持久化、缓存、日志与链路追踪 | SQL Server数据库、glue原生Cache模块、glue原生日志与监控组件 |

### 3.2 核心流转逻辑
1. 设计端：用户在可视化设计器中完成流程建模，生成统一格式的流程定义JSON，提交后存入数据库。
2. 执行端：业务请求通过 glue 框架承载的统一API接入，路由层根据流程类型分发至对应引擎；引擎加载流程定义、解析元模型后执行对应逻辑，缓存能力复用框架Cache模块。
3. 监控端：双引擎执行过程中通过 glue 框架原生日志与链路能力输出运行数据，同时结构化日志落库，支持全链路查询与审计。

## 四、统一元模型设计
### 4.1 设计思路：统一显式边集存储
针对两类流程连线存储机制的差异，**底层统一采用「显式边集」作为唯一存储标准**，节点与连线为两个独立扁平集合，所有流转关系通过连线对象显式定义。
- 对规则链引擎原生友好，直接匹配DAG执行模型；
- 对工作流引擎，加载时可无损转换为邻接表（对应WF隐式节点属性连线），运行时性能无损耗；
- 可视化设计器直接读取边集渲染连线，无需遍历节点属性，渲染与交互效率更高。

### 4.2 统一JSON Schema规范
所有流程定义均遵循同一套JSON结构，通过`type`字段区分流程类型，字段完全兼容两种模式。
```json
{
  "id": "流程唯一标识",
  "name": "流程名称",
  "type": "WORKFLOW | RULE_CHAIN",
  "version": "版本号",
  "variables": [{"name": "变量名", "type": "数据类型", "default": "默认值"}],
  "settings": {},
  "nodes": [
    {
      "id": "节点ID",
      "name": "节点显示名",
      "type": "节点类型",
      "position": {"x": "横坐标", "y": "纵坐标"},
      "config": {}
    }
  ],
  "connections": [
    {
      "id": "连线ID",
      "fromId": "源节点ID",
      "toId": "目标节点ID",
      "label": "连线标签",
      "relationType": "关系类型",
      "condition": "条件表达式",
      "isDefault": false
    }
  ]
}
```

### 4.3 双模型无损映射机制
工作流模式的隐式连线属性，可与统一显式边集实现无损双向映射，兼容WF流程图的所有节点类型：

| WF流程图节点属性 | 统一显式边集映射规则 |
|------------------|----------------------|
| FlowStep.Next | 生成1条普通连线，fromId=当前节点ID，toId=后继节点ID |
| FlowDecision.True | 生成1条条件连线，label="True"，relationType="CONDITION" |
| FlowDecision.False | 生成1条条件连线，label="False"，isDefault=true |
| FlowSwitch.Cases | 生成多条分支连线，label=分支值，对应不同目标节点 |
| FlowSwitch.Default | 生成1条默认连线，isDefault=true |

## 五、数据库设计（SQL Server）
### 5.1 命名规范
- 所有业务表统一添加`sch_`前缀，符合企业级数据库命名规范。
- JSON类型字段统一使用`nvarchar(max)`存储，兼容SQL Server原生JSON函数。
- 时间字段统一使用`datetime2(3)`，支持毫秒级精度，默认值使用`GETDATE()`。

### 5.2 核心表结构
共5张核心表，分为通用基础表、工作流引擎专属表、规则链引擎专属表三类。

#### 1. 通用基础表：sch_flow_definition
双引擎共用的流程定义存储表，支持多版本管理，是所有流程的元数据入口。
| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | nvarchar(64) | 主键，记录唯一ID |
| flow_code | nvarchar(64) | 流程编码，同一流程多版本共用 |
| name | nvarchar(128) | 流程显示名称 |
| flow_type | nvarchar(32) | 流程类型：WORKFLOW / RULE_CHAIN |
| version | int | 版本号，同一flow_code下递增 |
| model_content | nvarchar(max) | 完整流程模型JSON |
| status | tinyint | 状态：0=停用，1=启用 |
| create_time / update_time | datetime2(3) | 创建与更新时间 |

#### 2. 工作流引擎专属表
- **sch_workflow_instance**：工作流实例持久化表，存储长时运行流程的状态、变量、当前节点等快照，对应WF的实例存储能力。
- **sch_workflow_node_log**：工作流节点执行日志表，全链路记录每个节点的执行状态、入参出参、异常信息，对应WF的跟踪服务。

#### 3. 规则链引擎专属表
- **sch_rulechain_exec_log**：规则链执行总表，记录单次消息处理的整体结果、耗时、载荷信息。
- **sch_rulechain_node_log**：规则链节点执行明细表，记录单条执行链路上每个节点的处理状态，用于问题排查与性能分析。

## 六、双引擎内核设计
### 6.1 工作流引擎（对标微软WF能力）
面向长周期、有人工参与、需要状态持久化的业务流程，核心能力对齐WF框架核心特性；缓存与日志能力全部复用 glue 框架原生组件。
1. **核心能力**
    - 支持流程图、状态机两种建模方式，覆盖顺序流转、条件分支、并行、回退、跳转等复杂流程逻辑。
    - 原生支持实例持久化、书签暂停、人工任务、事务补偿、会签/或签等BPM特性，实例生命周期可达天/月级。
    - 执行到持久点自动将状态落库，空闲时释放内存资源，支持从任意节点恢复执行；热点流程定义与实例数据通过 glue Cache 模块缓存，提升加载性能。
2. **核心技术对象**
    - WorkflowInstance：工作流实例对象，管理单条流程的生命周期。
    - ActivityHandler：活动处理器基类，所有自定义节点的统一接口。
    - ExecutionContext：执行上下文，承载流程变量、节点状态与运行时数据。
    - PersistenceService：持久化服务，负责实例状态的保存与加载。

### 6.2 自研规则链引擎
纯Go原生实现，无第三方规则引擎依赖，面向高并发、无状态、事件驱动的实时数据处理场景；基于 glue 框架承载，复用框架缓存、日志能力。
1. **核心架构分层**
    - 模型加载层：解析统一JSON模型、DAG拓扑环校验、基于 glue Cache 模块构建流程定义缓存、支持热更新。
    - 执行内核层：执行器调度、上下文管理、连线路由、异常捕获、链路推进。
    - 节点扩展层：节点处理器SPI接口、节点工厂、内置节点集（过滤、转换、HTTP、日志等）。
    - 监控日志层：基于 glue 框架原生日志与链路追踪能力实现执行日志输出、链路埋点、性能指标采集，无需额外集成第三方组件。
2. **核心执行流程**
    1. 预加载校验：流程入库后异步预加载，通过Kahn拓扑排序校验DAG合法性，构建邻接表并写入 glue Cache 缓存。
    2. 上下文创建：消息入站时生成独立执行上下文，承载消息载荷、全局变量与执行链路。
    3. 节点执行：从起始节点开始，通过节点工厂获取对应处理器执行业务逻辑。
    4. 连线路由：根据节点执行结果匹配对应`relationType`的出站连线。
    5. 链路推进：迭代执行所有匹配的后继节点，直至无可用连线，链路终止。
    6. 结果落库：异步写入执行总表与节点明细日志，同时通过框架日志组件输出结构化运行数据。
3. **核心技术对象**
    - RuleChainExecutor：规则链执行器，对外统一入口，支持同步调用、异步协程执行、协程池限流。
    - RuleContext：规则执行上下文，单次执行的全量数据载体。
    - IRuleNodeHandler：节点处理器接口，所有自定义节点必须实现。
    - ConnectionRouter：连线路由器，根据执行结果匹配出站连线，是链路推进的核心。

### 6.3 跨引擎联动机制
两种引擎通过标准化节点实现双向联动，能力互补覆盖全场景：
1. **工作流调用规则链**：工作流内置「规则链调用节点」，执行到该节点时传入上下文数据同步调用规则链，执行完成后将结果写回流程变量，继续流转。适用于审批前数据校验、自动计算等场景。
2. **规则链触发工作流**：规则链内置「启动工作流节点」，当消息满足触发条件时，异步/同步启动对应工作流实例。适用于告警自动开工单、数据达标自动发起审批等场景。

## 七、统一可视化设计层
### 7.1 设计器核心能力
- 一套前端画布支持两种流程模式切换，拖拽交互、连线操作、属性配置完全一致。
- 内置节点工具箱，根据当前模式自动加载对应节点类型，避免跨模式混用。
- 支持实时校验、版本保存、预览调试、流程导入导出。
- 推荐基于 AntV X6 / LogicFlow 二次开发，国内生态成熟，自定义节点与连线成本低。

### 7.2 双模式切换机制
- **工作流模式**：加载人工任务、网关、事件、子流程等节点，连线支持条件表达式，允许循环、回退，支持泳道与权限配置。
- **规则链模式**：加载过滤、转换、动作、集成类节点，连线默认带Success/Failure类型，自动校验DAG结构，禁止循环连线。

## 八、技术选型方案
| 模块 | 选型方案 | 说明 |
|------|----------|------|
| 前端设计器 | Vue3 + AntV X6 | 成熟的图编辑引擎，自定义节点与连线扩展成本低，支撑双模式可视化建模 |
| 后端服务 | Go + glue 微服务框架（github.com/zhiyunliu/glue） | 轻量级Go微服务框架，提供依赖注入、组件化编排、统一中间件抽象能力，支撑双引擎服务快速开发与治理 |
| 核心数据库 | SQL Server 2016+ | 企业级关系型数据库，适配项目存储规范，支持事务、JSON查询、审计等能力 |
| 缓存中间件 | glue 原生 Cache 模块 | 框架内置缓存抽象层，原生支持Redis驱动，通过统一接口实现流程定义、热点实例数据的缓存管理，无需额外集成第三方Redis客户端 |
| 日志与监控 | glue 框架原生日志与链路追踪能力 | 框架内置结构化日志、全链路追踪、运行指标采集能力，覆盖双引擎执行日志、异常告警、性能监控需求，无需额外引入第三方监控组件 |

## 九、核心优势与边界说明
### 9.1 核心优势
1. **体验与存储统一**：一套设计器、一套存储结构、一套API，降低学习、运维与开发成本。
2. **能力全面覆盖**：同时覆盖长时业务流程与实时事件处理两类核心场景，满足企业全流程需求。
3. **架构高可用**：双引擎隔离部署、独立扩容，故障互不影响，系统稳定性更强。
4. **自主可控、依赖精简**：规则链引擎纯自研，无第三方开源引擎依赖；缓存、日志、服务治理全链路复用 glue 框架原生能力，减少外部组件依赖，降低运维复杂度。
5. **企业级适配**：全面适配SQL Server数据库，支持事务、审计、多版本等企业级特性。

### 9.2 设计边界
1. 两种模式的节点不可直接混用，禁止在规则链中加入人工任务等长时节点，避免模型混乱。
2. 跨引擎联动仅通过标准化调用节点实现，不支持流程嵌套与直接节点跳转，保证引擎边界清晰。
3. 规则链引擎默认采用DAG模型，不原生支持循环与回退，如需循环逻辑需通过工作流引擎实现。

## 十、落地实施建议
1. **第一阶段：基础能力落地**
    完成统一元模型定义、SQL Server表结构开发、基于 glue 框架搭建后端服务底座，实现规则链引擎核心内核与基础节点开发、简单可视化设计器落地，达成规则链全流程可用。
2. **第二阶段：工作流引擎补齐**
    开发工作流引擎核心调度、持久化、人工任务能力，补齐流程图与状态机模型，复用框架Cache与日志能力，实现双引擎基础联动。
3. **第三阶段：能力增强与优化**
    完善权限管理、多版本管理、热更新等企业级特性，扩展更多内置节点，基于框架监控能力完善运营大盘，优化执行性能。
