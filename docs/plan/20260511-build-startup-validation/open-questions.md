# Build/Startup 待澄清项（Open Questions）

## 1. 依赖来源（Dependency Source）

### Q1. 运行时依赖清单的权威来源是什么？
- 现状：依赖可能分散在 docker-compose、环境变量模板、启动脚本与代码默认值中。
- 影响：若无单一权威清单，L2/L3 验收时容易出现“本地可跑、环境不可复现”。
- 需确认：
  - 以哪个文件或文档作为依赖基线。
  - 是否允许“隐式依赖”（未在文档登记但运行时必须存在）。
- 建议结论：指定 1 个主清单 + 1 个补充清单，验收仅按清单判定。

### Q2. 第三方服务/中间件是否区分“必需”与“可降级”？
- 现状：部分依赖在开发环境可跳过，在测试/生产可能必需。
- 影响：健康检查标准与启动成功标准会被混淆。
- 需确认：
  - 每个依赖的级别（必需/可降级/可选）。
  - 不可用时系统的预期行为（失败退出或降级运行）。

## 2. 联动验证范围（Integration Validation Scope）

### Q3. E2E 最小业务闭环覆盖到哪一层？
- 现状：存在“仅 API 成功”与“前后端全链路成功”两种口径。
- 影响：L4 通过标准不一致，评审结果不可比。
- 需确认：
  - 是否必须包含前端入口、后端处理、存储落地三段。
  - 是否接受“仅后端链路”的替代路径（如前端暂未接入）。

### Q4. 配置管理与运行时执行两个子域是否需要同批次联动验收？
- 现状：仓库包含 config-management 与 runtime-execution 两套能力域。
- 影响：若不明确联动范围，可能只验证单域导致回归遗漏。
- 需确认：
  - 本轮验收是单域内闭环还是跨域联调。
  - 若跨域，最小必测场景列表是什么。

## 3. 健康检查标准（Health Criteria）

### Q5. 健康检查接口成功判定采用何种统一规范？
- 现状：可能存在 HTTP 状态码、业务 code 字段、文本响应等多种判定方式。
- 影响：自动化脚本难以统一，人工判断偏差大。
- 需确认：
  - 统一成功标准（例如 HTTP 2xx 且业务 code=200）。
  - 异常场景是否区分 readiness 与 liveness。

### Q6. 健康检查的稳定性阈值如何定义？
- 现状：单次通过可能掩盖抖动问题。
- 影响：L3 通过后仍可能在短时间内失败。
- 需确认：
  - 连续成功次数与检查间隔（例如 3 次，间隔 10 秒）。
  - 允许失败重试的上限与判定窗口。

## 4. 建议的确认输出（可直接用于评审）
- 输出物 1：依赖分级清单（必需/可降级/可选）。
- 输出物 2：L4 最小 E2E 场景列表（输入、步骤、预期结果）。
- 输出物 3：统一健康检查判定规则（成功码、重试策略、超时阈值）。
- 输出物 4：本轮验收范围声明（单域或跨域，覆盖边界）。
